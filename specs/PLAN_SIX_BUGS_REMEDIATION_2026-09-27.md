## Критическое уточнение терминов

«Первый лог не срабатывает» означает не первый приём пищи за всё время жизни
аккаунта и не показ celebration.

Правильный сценарий:

1. Пользователь открывает приложение или начинает новую пользовательскую сессию.
2. Делает первую попытку залогировать еду: вводит данные, отправляет фото, текст
   или голос и подтверждает сохранение.
3. Первая попытка не приводит к сохранённой записи в журнале.
4. Пользователь вынужден повторно вводить или отправлять те же данные.
5. Повторная попытка срабатывает.

Это P0-дефект потери пользовательского действия. Он не связан с однократной
анимацией «первый приём пищи» и не должен исправляться account-scoped флагом.

## 1. Большой голосовой текст на Android

В production найдены две попытки около 01:22 по Москве. Обе завершились HTTP
422; короткая повторная фраза после этого прошла.

Подтверждённая цепочка:

1. Flutter устанавливает `_fromVoice` только после `finalResult`.
2. Android не гарантирует такой callback до нажатия «Отправить».
3. Голосовой текст пришёл в backend как `is_voice=false`.
4. ASR-текст содержал фрагментарную пунктуацию.
5. Backend потребовал точного совпадения числа текстовых сегментов и продуктов.
6. Весь результат был отклонён общим 422.

Исправление:

- хранить voice provenance с начала записи или первого partial;
- передавать `input_source: voice|text` независимо от `finalResult`;
- идентифицировать нативные speech-сессии и отбрасывать поздние callback;
- заменить точное равенство количества сегментов проверкой покрытия текста,
  дубликатов и confidence;
- возвращать typed clarification вместо общей ошибки.

## 2. Совет по завтраку 04.09

Для точной фразы backend получил успешный ответ AI-провайдера, вернул HTTP 200
и сохранил ответ. Поэтому менять генерацию ответа на backend без нового
доказательства нельзя.

Не доказано, дошёл ли результат до пользовательского UI. Требуется сквозная
цепочка:

`client_operation_id → HTTP request → backend run → response → rendered → reload`.

Исправление здесь — наблюдаемость и клиентский regression test. Если ответ
успешно сохранён на backend, но не был показан, mobile должен сообщить отдельную
ошибку `response_not_rendered`.

## 3. Противоречивые данные этикетки 25.08

На этикетке были явные значения 42,9 ккал/100 г, 167 ккал/порцию и масса
порции 390 г. Модель смешала значения на 100 г и порцию, а в другой попытке
прочитала кДж как ккал.

Backend правильно запретил сохранение противоречивых данных. Нельзя отключать
этот guard.

Исправление:

- каноническая OCR-сущность `value + unit + basis + raw_text + confidence`;
- детерминированная нормализация kcal/kJ после OCR;
- независимость от конкретного имени raw-поля `calories`;
- раздельные `per_100g`, `per_serving`, `per_piece`;
- структурированные error codes;
- UI уточнения вместо тупиковой общей ошибки;
- регрессионная fixture из точного обезличенного production payload.

## 4. Apple Sign In возвращает на «Худей просто»

`loginWithTokens` публикует authenticated state раньше завершения onboarding
sync. Router видит авторизованного пользователя с `onboardingDone=false` и
отправляет его на `/onboarding`. После размонтирования login screen дальнейшая
операция может остановиться на проверке `mounted`.

Исправление:

- единый `AuthHandoffCoordinator` для Apple, регистрации и login;
- state machine `exchanging → syncingOnboarding → loadingUser → authenticated`;
- публикация authenticated только после завершения обязательного handoff;
- состояние `authCompleting`, при котором router не делает промежуточный redirect;
- идемпотентность повторного callback и cold start;
- отсутствие зависимости бизнес-операции от lifecycle login screen.

## 5. Первая попытка логирования в сессии не сохраняется

### Что уже установлено

Историческое воспроизведение особенно явно зафиксировано для первого фото:
первая отправка после входа в flow не обрабатывалась или не доходила до
сохранения, повторная работала.

В текущем коде есть несколько возможных точек потери, которые нельзя смешивать:

1. cold start камеры или speech engine;
2. первый read временного файла фото до завершения записи;
3. потеря результата между provider, route и resume lifecycle;
4. parser вернул ошибку, которую mobile проглотил и перевёл в другой flow;
5. действие пользователя проигнорировано локальным guard без видимой ошибки;
6. pre-save side effect выполняется до основного POST сохранения;
7. POST сохранения не был отправлен, завершился ошибкой или вернул некорректный
   контракт;
8. backend сохранил meal, но mobile не подтвердил успех и пользователь повторил
   операцию.

Отдельный риск текущего незакоммиченного кода: несколько save-flow вызывают
`prepareFirstMealCelebration()` с дополнительным GET до основного
`POST /api/meals/add_selected`. Celebration не должен находиться на критическом
пути сохранения и не должен блокировать первую попытку.

### Обязательная диагностика до фикса

Для каждой новой сессии выполнить матрицу `text/photo/voice/manual` и записать
стадии одной операции с единым `client_operation_id`:

1. `input_started`;
2. `input_acquired`;
3. `recognition_started`;
4. `recognition_completed`;
5. `save_started`;
6. `save_response_received`;
7. `save_persisted`;
8. `success_rendered`.

Нужно определить первую отсутствующую стадию и только после этого выбирать fix.

### Архитектурное исправление

- Ввести единый `MealLogOperation` для всех источников.
- Создавать UUID операции до первого асинхронного действия.
- Сделать стадии явным immutable state, не распределять их по widget-local bool.
- Убрать celebration, feedback prompt и coach advice из критического пути save.
- Save считается успешным только после server acknowledgment с operation ID,
  количеством сохранённых позиций и IDs записей.
- Повтор с тем же idempotency key не создаёт дубль.
- При смене route/background операция остаётся в provider/repository до
  терминального результата.
- Любой non-terminal timeout переводится в явную ошибку и durable report.

### Критерии готовности

- Первая попытка после cold start и после новой app session сохраняется с
  первого раза.
- Проверены text, photo и voice; photo отдельно прогнан после первого camera
  permission.
- 20 последовательных чистых запусков: 20/20 первых операций заканчиваются
  сохранением или конкретной видимой ошибкой, но никогда не исчезают молча.
- Повтор запроса не создаёт двойную запись.

## 6. Android сохраняет только последнюю строку голоса

В `HEAD` есть `VoiceSessionMachine`, которая накапливает текст между speech
sessions. Unit-тесты проходят, но нативный Android lifecycle не проверен.

Исправление и проверка объединяются со случаем 1:

- отдельные committed и partial transcript;
- session ID для callback;
- restart без сброса UI;
- отправка без зависимости от final result;
- Android device test с паузами, late callback и несколькими restart.

## 7. Обязательное журналирование ошибок и Telegram-отбивки

### Почему текущей системы недостаточно

- `meal_processing_run` создаётся только после получения запроса backend.
- Клиентский сбой до HTTP-запроса не оставляет backend-записи.
- Несколько Flutter `catch` показывают общий snackbar и теряют тип, стадию и
  correlation ID.
- Текущий Telegram-outbox ориентирован на пользовательские оценки, а не на
  технические сбои логирования.

### Определение инцидента

Инцидентом считается любая операция логирования, которая не завершилась одним
из разрешённых терминальных результатов:

- `saved` — еда сохранена и успех показан пользователю;
- `clarification_required` — показан конкретный вопрос, операция продолжима;
- `not_food` — показан корректный и понятный domain-result;
- `cancelled_by_user` — пользователь явно отменил действие.

Ошибка создаётся для:

- transport failure/timeout;
- HTTP 4xx/5xx, кроме ожидаемых typed domain outcomes;
- пустого или невалидного API-контракта;
- parser/recognition exception;
- `added=0` при подтверждённом сохранении непустого списка;
- потери operation state при route/lifecycle;
- backend success без отображения результата;
- локального Flutter exception;
- зависшей операции без терминального результата.

### Mobile-контур

1. Создавать `client_operation_id` в начале каждой попытки.
2. Сохранять error event в локальный durable outbox до попытки отправки.
3. Отправлять событие в отдельный idempotent endpoint, например
   `POST /api/meal-log-incidents`.
4. Если backend недоступен, сохранять событие локально и повторять после
   восстановления сети или следующего запуска.
5. Не использовать raw photo/audio, токены и чувствительные payload.
6. Не допускать рекурсивной генерации инцидентов самим incident reporter.

### Backend-контур

1. Добавить append-only `meal_log_incident` с unique `event_id`.
2. Связывать incident с `client_operation_id`, `correlation_id`, `run_id` и
   `save_operation_id`, если соответствующая стадия успела возникнуть.
3. В одной транзакции сохранять incident и создавать запись отдельного
   `incident_telegram_outbox`.
4. Backend failure в `meal_processing_run` также должен создавать incident без
   ожидания клиентского отчёта.
5. Watchdog помечает зависшие `started` runs и ставит их в outbox.
6. Дедупликация выполняется по `event_id`; повторная доставка одного события не
   создаёт вторую Telegram-отбивку. Новая пользовательская попытка — новый
   incident и новая отбивка.
7. Telegram failure не влияет на пользовательский API; worker использует
   retry/backoff и сохраняет историю попыток.

### Содержание Telegram-сообщения

- 🚨 `Meal logging failed`;
- источник: text/photo/voice/barcode/manual/chat;
- стадия, на которой остановилась операция;
- безопасный error code и HTTP status;
- platform и app version;
- длительность и номер пользовательской попытки;
- `client_operation_id`, `correlation_id`, `run_id` при наличии;
- время UTC и локальный offset;
- отметка, дошёл ли основной запрос до backend;
- отметка, была ли последующая повторная попытка успешной.

Нельзя отправлять токены, полные фотографии, аудио, секретные URL и
нефильтрованные stack trace. Текст еды допускается только в редактированном
безопасном виде и после отдельного решения о privacy.

### Важное ограничение

Если одновременно недоступен основной backend, mobile не может мгновенно
доставить Telegram через тот же backend. Такой incident должен лежать в
локальном outbox и уйти после восстановления связи. Для мгновенного сообщения
при полной недоступности backend потребуется независимый внешний crash/error
collector — это отдельное инфраструктурное решение.

### Критерии готовности

- Каждый искусственно вызванный failure появляется в backend incident table.
- Владелец получает одну Telegram-отбивку на одну неуспешную операцию.
- Client-before-request failure доставляется после восстановления сети.
- Backend 422/500/timeout и `response_not_rendered` различимы.
- Telegram restart не теряет события и не создаёт логических дублей.

## Фазы реализации

### Фаза 0 — доказать место потери первой операции

- Ввести временную сквозную трассировку стадий `MealLogOperation`.
- Воспроизвести первую попытку после cold start и новой app session для text,
  photo и voice.
- Найти первую отсутствующую стадию между `input_started` и
  `success_rendered`.
- Зафиксировать доказанную первопричину до изменения рабочего поведения.

Результат фазы: воспроизводящий тест и однозначная карта места потери.

### Фаза 1 — исправить первую попытку логирования

- Реализовать единый lifecycle `MealLogOperation`.
- Исправить доказанную в фазе 0 причину.
- Убрать некритические side effects с пути основного сохранения.
- Добавить server acknowledgment и идемпотентность повторной отправки.
- Подтвердить 20/20 успешных первых операций либо конкретных видимых ошибок.

Результат фазы: первая попытка не исчезает и не требует повторного ввода.

### Фаза 2 — журнал ошибок и Telegram-отбивки

- Добавить mobile durable outbox.
- Добавить idempotent incident endpoint и append-only incident storage.
- Добавить отдельный Telegram-outbox технических инцидентов.
- Связать client и backend failures сквозными идентификаторами.
- Добавить watchdog зависших операций, dedupe и retry.

Результат фазы: каждая неуспешная операция видна в backend и Telegram.

### Фаза 3 — единый Android voice pipeline

- Объединить исправление случаев 1 и 6.
- Сохранить voice provenance независимо от `finalResult`.
- Исправить накопление строк, restart и поздние callback.
- Сделать backend-сегментацию устойчивой к ASR-пунктуации.

Результат фазы: длинный голосовой ввод сохраняет весь текст и корректно
обрабатывается.

### Фаза 4 — атомарный Apple auth handoff

- Реализовать единый auth coordinator.
- Устранить промежуточный redirect на onboarding.
- Подтвердить сценарий реальным Apple Sign In.

Результат фазы: после авторизации пользователь не возвращается на «Худей
просто».

### Фаза 5 — безопасное распознавание этикеток

- Нормализовать OCR energy unit и nutrition basis.
- Сохранить fail-closed validator.

Результат фазы: корректные данные сохраняются, неоднозначные требуют понятного

### Фаза 6 — подтверждение доставки chat-ответа

- Добавить API → render → reload acknowledgment.
- Проверить случай фразы про завтрак без необоснованного изменения backend.

Результат фазы: можно доказать получение или точную стадию потери ответа.

### Фаза 7 — общая регрессия и решение о выпуске

- Выполнить полную автоматическую и device/E2E матрицу.

## Запрещённые быстрые исправления

- Не трактовать случай 5 как first-meal celebration или account-scoped флаг.
- Не добавлять `Future.delayed` вместо исправления lifecycle/state race.
- Не проглатывать exception после показа общего snackbar.
- Не считать HTTP 200 доказательством, что пользователь увидел результат.
- Не отправлять Telegram напрямую из Flutter с bot token.
- Не ослаблять label validator.
- Не объявлять Android-баг закрытым только по Dart unit-тестам.

## Definition of Done

- Первая операция логирования в новой сессии работает с первого раза.
- Каждая неуспешная операция сохраняется и приводит к Telegram-отбивке.
- Для каждого события видна точная стадия отказа и сквозные идентификаторы.
- Все шесть исходных случаев имеют regression evidence.
- Голос проверен на Android device, Apple auth — на iPhone.
- Точный payload этикетки проходит безопасную fixture-проверку.
- Нет silent catch, который оставляет владельца без технической отбивки.
- Production deploy, миграции и release выполняются только после отдельного
  разрешения владельца.
