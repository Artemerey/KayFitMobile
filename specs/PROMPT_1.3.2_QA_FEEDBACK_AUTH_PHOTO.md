# Prompt: KayFit 1.3.2 — исправления по ручному QA сборки 1.3.1+12

## Роль и цель

Ты senior Flutter + FastAPI engineer. Исправь полный пользовательский сценарий по результатам ручного QA iPhone-сборки `1.3.1+12`. Работай одновременно с двумя репозиториями:

- mobile: `/Users/user/Desktop/КУРСОР/mobileKayfit`
- backend: `/Users/user/Desktop/КУРСОР/CaloriesApp_backend`

Не ограничивайся визуальным патчем. Найди первопричину каждого дефекта, добавь автоматические регрессионные тесты, проверь реальные API-контракты и подготовь новую тестовую сборку. Не меняй production bundle id/signing в коммите и не коммить временные dev-entitlements.

## Зафиксированные дефекты

1. На iPhone у иконки KayFit видны две жёлтые линии сверху. Это не утверждённый вид иконки.
2. Пользователь закончил онбординг, оставил комментарий и поставил лайк. UI показал успех, но владельцу не пришло Telegram-уведомление. Требование: владелец должен видеть в Telegram **каждую** оценку — и like, и dislike, с комментарием или без него.
3. После оценки плана пользователя перебросило на sign-in так, будто произошла ошибка/истекла сессия. Для нового неавторизованного пользователя это нормальное продолжение онбординга, а не ошибка. Нужен позитивный переход с понятным текстом: «Отлично! План готов. Чтобы сохранить его и приступить к цели, зарегистрируйтесь или войдите».
4. После добавления еды через текст (`шоколад`) не появились 👍/👎 для оценки конкретного распознавания. При 👎 пользователь должен иметь возможность указать причину и написать корректировку.
5. Первое фото после открытия photo-flow снова не обрабатывается; повторная попытка может сработать. Этот исторический баг считался исправленным, но воспроизводится в `1.3.1+12`.

## Важное различие для feedback UX

Не смешивай две сущности:

- `onboarding_plan` — оценка рассчитанного плана;
- `meal_save` / recognition result — оценка конкретного результата фото, текста, голоса, штрихкода, чата, рецепта или копирования.

Оценка еды должна быть однозначно привязана к операции/результату, который пользователь только что сохранил. Нельзя показывать общий вопрос без target ID и нельзя молча скрывать feedback UI при нарушении контракта.

## Фаза 0. Воспроизведение и карта причин

До изменений:

1. Воспроизведи все пять дефектов на чистой установке и на установке с сохранившимся Keychain-токеном.
2. Сними безопасные логи (без токенов, паролей и персональных данных):
   - маршрут до/после оценки онбординга;
   - наличие `feedback_target_id` в ответе каждого save endpoint;
   - создание записи `user_feedback` и строки `feedback_telegram_outbox`;
   - состояние worker и причины недоставки Telegram;
   - последовательность camera permission → capture → enqueue → recognition outcome для первого фото.
3. Проверь production-конфигурацию Telegram feedback: `FEEDBACK_TELEGRAM_ENABLED`, наличие bot token/chat id, запуск background worker, pending/failed outbox. Значения секретов не выводить.
4. Составь короткую таблицу «симптом → первопричина → исправление → тест». Не переходи к реализации, пока для каждого дефекта не установлена проверяемая причина.

## Фаза 2. Гарантированная Telegram-доставка каждой оценки

Исследуй текущие:

- `backend/app/api/feedback.py`
- `backend/app/services/feedback_service.py`
- Telegram outbox worker и `docs/FEEDBACK_DEPLOYMENT_RUNBOOK.md`
- mobile `lib/core/feedback/*`

Требования:

1. Каждый успешно принятый `POST /api/feedback` атомарно создаёт feedback + outbox event.
2. Worker отправляет владельцу Telegram-сообщение для **каждого** `like` и `dislike`, независимо от наличия reasons/comment.
3. Сообщение содержит минимум: 👍/👎, тип (`onboarding_plan`/`meal_save`), source (`photo/text/...`), reasons, comment, UTC-время и короткий feedback/event ID для поиска дублей.
4. Telegram I/O не должно ломать клиентский запрос: API подтверждает сохранение после записи в БД/outbox, доставка повторяется с retry/backoff.
5. Не терять события при рестарте. Повторная доставка допустима только в рамках документированной at-least-once семантики и должна быть заметна по ID.
6. Добавить health/diagnostic signal: pending count, oldest pending age, failed/retry count. Если Telegram отключён конфигурацией, это должно быть явно видно оператору.
7. В production включить feedback worker и корректный destination chat согласно существующему runbook. Секреты брать из установленной серверной конфигурации; не печатать и не добавлять в git.
8. Выполнить end-to-end smoke: отправить тестовые like и dislike через API/приложение и подтвердить фактическое получение двух Telegram-сообщений.

Критерий: пользователь видит «Спасибо» только после надёжной локальной постановки в очередь; владелец получает каждую оценку в Telegram. Offline feedback отправляется после восстановления сети/авторизации.

## Фаза 3. Позитивный handoff онбординг → регистрация

Исправь state machine, а не только строку ошибки.

Ожидаемый сценарий нового пользователя:

1. Заполнить онбординг.
2. Увидеть рассчитанный план.
3. Оставить или пропустить оценку.
4. Увидеть позитивный CTA/экран: «Отлично! План готов. Чтобы сохранить его и приступить к цели, зарегистрируйтесь или войдите».
5. Перейти в auth с вкладкой регистрации по умолчанию; вход остаётся доступен для существующего аккаунта.
6. После успешной регистрации pending onboarding submission и pending feedback связываются с user/server target, отправляются и пользователь попадает к своему плану.

Требования:

- не показывать `session expired`, красный error snackbar или иной текст сбоя для ожидаемого anonymous → auth перехода;
- logout старого Keychain-токена при reinstall выполнять тихо как техническую очистку, не выдавая её за ошибку пользователя;
- не терять onboarding answers, calculated plan, submission ID и feedback при переходе;
- исключить redirect loop `/login ↔ /journal-v2 ↔ /onboarding`;
- deep link/back/cold restart должны приводить в корректное состояние.

Добавь widget/router tests минимум для: fresh anonymous, stale Keychain token после reinstall, feedback like, feedback skip, регистрация success, возврат из auth.

## Фаза 4. 👍/👎 после каждого распознавания и сохранения еды

Проверь все источники: `photo`, `voice`, `text`, `barcode`, `chat`, `recipe`, `copy`.

1. Каждый успешный save endpoint обязан вернуть непустой `feedback_target_id` при `added > 0`.
2. Mobile обязан распарсить ID и показать feedback prompt после успешного сохранения, когда save/result sheet уже безопасно закрыт.
3. Нельзя использовать произвольный `Future.delayed` как единственную гарантию показа. Привяжи показ к жизненному циклу navigator/root overlay так, чтобы prompt не терялся при `pop`/route redirect.
4. Если контракт нарушен (`added > 0`, но ID пустой), записать диагностическое событие/лог и показать recoverable feedback action, а не молча ничего не делать.
5. 👍 можно отправить одним подтверждённым действием; комментарий остаётся опциональным.
6. 👎 открывает причины (`wrong_food`, `missing_item`, `extra_item`, `wrong_weight`, `wrong_calories`, `wrong_macros`, `recognition_too_slow`, `other`) и поле свободной корректировки.
7. Вопрос должен явно относиться к только что добавленному результату, например «Правильно распознали шоколад?».
8. Один save operation → не более одного feedback prompt и один стабильный target ID; повтор API с idempotency key не создаёт новый target.

Добавь contract/integration/widget tests по каждому из семи источников, включая конкретный текстовый кейс `шоколад`.

Критерий: после сохранения `шоколад` появляется 👍/👎; при 👎 можно выбрать причину и написать исправление; отправка создаёт feedback и Telegram notification.

## Фаза 5. Первое фото всегда распознаётся

Исследуй полный путь:

- `recognition_v2_screen.dart` / camera controller;
- возврат `XFile` через router;
- `photo_recognition_provider.dart` enqueue/drain;
- переход на result screen и active result provider;
- lifecycle `inactive/background/resumed`;
- camera permission на чистой установке.

Не возвращай старый picker retry вслепую. Найди текущую гонку в camera-controller flow.

Требования:

1. Кнопка затвора недоступна, пока controller не initialized и permission flow полностью не завершён.
2. Первый валидный tap создаёт ровно один непустой файл, добавляет ровно одну задачу в очередь и запускает ровно один API-запрос.
3. Capture state не теряется из-за dispose/pop/rebuild/provider autoDispose.
4. Ошибка permission/network/AI отображается явно с `Повторить`, но не превращается в вечный analyzing bubble.
5. Быстрый двойной tap дедуплицируется.
6. Background/resume сразу после снимка не теряет outcome.

Добавь:

- unit test state machine camera readiness/capture;
- widget test первого tap после выдачи permission;
- provider test enqueue → success/error;
- integration test «чистая установка → разрешить камеру → первый снимок → result»;
- ручной stress-test: 10 чистых запусков photo-flow, 10/10 первых снимков доходят до результата или явной ошибки.

## Definition of Done

- Все пять исходных дефектов воспроизведены до исправления и не воспроизводятся после.
- Каждая оценка сохраняется в БД и фактически приходит владельцу в Telegram.
- Новый пользователь воспринимает регистрацию как логичное завершение создания плана, а не как ошибку сессии.
- Feedback prompt появляется после каждого успешного сохранения из всех поддержанных источников.
- Первый снимок стабильно запускает распознавание.
- Иконка соответствует утверждённому master-asset.
- Добавлены автоматические регрессионные тесты; существующие тесты не сломаны.
- В финальном отчёте указаны: первопричины, изменённые файлы, результаты тестов, E2E-доказательства и оставшиеся риски.

Не объявляй задачу завершённой только по unit-тестам или наличию кода. Telegram и первое фото должны быть подтверждены реальным end-to-end тестом.
