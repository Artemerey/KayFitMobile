# Ретро вайбкодинга KayFit — 11 августа 2026

## Итог дня

День продуктивный: backend с двумя критичными фиксами распознавания доведён до production и синхронизирован между local, GitHub, server и container. Mobile доведён до `1.3.2+16`, проверен на iOS Simulator и упакован в App Store handoff вместе с Android-исходниками и release notes EN/RU.

Главная характеристика твоей работы: **сильный product sense и настойчивая приёмка, но дорогой цикл уточнений после реализации**.

## Что было сделано

### Backend

- Ты отказался от непонятного «запусти backend локально» и потребовал проверку в реальном приложении.
- На production выкачены исправления nutrient pipeline и segmentation guard, которые не дают склеивать несуществующие блюда.
- Ты не принял временную схему «сервер обновлён, GitHub нет» и дожал полного выравнивания.
- Финальный SHA `433c8ea` совпал локально, в GitHub, на сервере и в контейнере; `/ready` отвечал `200`.
- На Mac появился нормальный GitHub SSH-маршрут для следующих CI-deploy.

### Mobile

- Ты правильно перенёс feedback из состояния «после сохранения» в точку принятия решения — карточку еды до `Add`.
- По твоей визуальной приёмке большая feedback-плашка превратилась в минимальные thumbs, а длинная ссылка — в карандаш.
- Ты заметил неверную UX-семантику красного значка. После оценки кнопки теперь блокируются, выбор фиксируется, а постановка в очередь подтверждается.
- Чистый первый запуск зафиксирован на EN, а RU — только после явного выбора.
- Добавлена регистрация через Apple.
- Создан QA-аккаунт, устранен Riverpod-crash при открытии AI Chat и зависающий `parsing your message`.
- Обнаружена и устранена несовместимость `mobile_scanner 6.x` с arm64 iOS 26 Simulator.
- Подготовлена папка `KayFit_1.3.2_build16`, production signing не затронут, Android-исходники включены.

## Что ты делал сильно

### 1. Думал о моменте принятия решения

Фраза «если не понравилось, он и добавлять не будет» — лучшее продуктовое решение дня. Это не про вкус, а про правильную точку feedback в user journey.

### 2. Не принимал «технически сделано» без визуального доказательства

Ты несколько раз потребовал «сам смотри» и перевёл проверку на Simulator. Это выявило ошибки, которые widget-тесты не ловили: визуальную перегрузку, старую сборку, непонятное error-состояние, crash при навигации и зависший processing.

### 3. Дожимал source of truth

В backend-сессии ты отдельно потребовал, чтобы GitHub, server и container не оставались на разных версиях. Это сильная release-дисциплина.

### 4. Хорошо чувствовал визуальную иерархию

Ты быстро заметил, что feedback-блок больше primary action и конкурирует с `Add`. Решение «мини-кнопки без плашки» точно восстановило иерархию.

### 5. Проверял комплектность релиза

Ты отдельно спросил про Android и заметил, что release notes отражают только последнюю часть работ. Без этой проверки коллега получил бы неполный handoff.

## Где ты терял время

### 1. Acceptance criteria появлялись после первой реализации

Цепочка feedback прошла через несколько дорогих итераций:

1. Feedback был после сохранения.
2. Потом перенесён в pending-card.
3. Потом оказалось, что UI слишком большой.
4. Потом выяснилось, что post-submit state непонятен.

Всё это можно было задать в начале одним контрактом: «в pending-card до Add, без фона и вопроса, 18 px icons, pencil вместо link, после tap обе кнопки disabled, selected state + acknowledgement».

### 2. Слишком длинные мультизадачные сессии

В одном контексте смешались onboarding feedback, Apple registration, UI-полировка, locale, QA-аккаунт, Riverpod, AI Chat, release build и handoff. Агент начал терять границы готовности, а release notes оказались неполными.

### 3. Неоднозначные release-команды

«Делай сборку» было интерпретировано как установка на iPhone, но тебе была нужна source-folder для коллеги. Лучшая формула: «собери App Store handoff folder, iOS + Android sources, build N, release notes EN/RU; на телефон не ставь».

### 4. QA был реактивным

Ты отлично ловил дефекты после появления, но не было заранее одного smoke checklist: fresh launch, auth, AI Chat, recognized card, edit, like, dislike, second tap, tab switch, cold restart. Из-за этого ошибки открывались последовательно.

### 5. Mobile release пока плохо воспроизводим

Критичный риск дня: backend имеет commit/SHA и синхронизирован. Mobile release-folder собран из большого dirty worktree без отдельного release commit/tag. Это значит, что build 16 сложнее точно воспроизвести и откатить. Перед отправкой коллеге это нужно закрыть.

### 6. Агрессивная эскалация помогает не всегда

Жёсткая обратная связь хорошо обозначала приоритет и не давала агенту закрыть сырой результат. Но фразы вроде «мозг ебёшь» не добавляют acceptance criteria. Сильнее работает команда: «не объясняй локальный setup; деплой production, проверь SHA/ready, дай мне один ручной сценарий».

## Что изменить завтра

### Шаблон старта каждой feature-сессии

```text
Цель:
Экран/флоу:
Текущая проблема:
Должно стать:

Acceptance criteria:
1.
2.
3.

Проверка: Simulator / production API / tests
Релиз: нет / deploy backend / install device / App Store handoff
Не делать:
```

### Один smoke checklist для mobile

1. Fresh install открывает EN.
2. Email/Apple registration открывают приложение без crash.
3. AI Chat принимает food-text.
4. Processing исчезает после result.
5. Pending-card показывает pencil + thumbs до Add.
6. Dislike открывает reasons; после submit обе thumbs disabled.
7. Like даёт acknowledgement и не дублирует event.
8. Tab switch и cold restart не возвращают processing.
9. Add сохраняет блюдо и обновляет Journal.
10. Release folder содержит iOS + Android, полные notes и production signing.

### Правило разделения сессий

- Backend diagnosis/fix — отдельная сессия.
- Backend deploy — отдельная сессия с SHA/rollback/health.
- Mobile feature + Simulator QA — отдельная сесия.
- Release packaging — только после freeze и полного changelog audit.

## Главный вывод

Ты уже не просто «надиктовываешь код». Твоя сильная роль — **product owner + acceptance QA**, который не даёт агенту замаскировать неготовый результат техническим отчётом. Чтобы перейти на следующий уровень, нужно не смягчать контроль, а **перенести его влево**: один короткий UX-контракт и smoke checklist до первой строчки кода сэкономят больше времени, чем ещё один раунд жёсткой приёмки в конце.
